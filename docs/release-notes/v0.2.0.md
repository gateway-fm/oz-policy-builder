# v0.2.0 release notes (draft)

Not yet released. Entries are added as changes land, in the commit that makes them.

## Breaking changes

- **An uncapped grant needs an explicit acknowledgement.** `UserDecisions` gains
  `unlimited_calls_acknowledged`, mirroring `no_expiry_acknowledged`; an absent field reads as
  `false`. A decisions document with `max_calls: null` (or no `max_calls`) and no
  acknowledgement is now refused with an `E_NEEDS_DECISION` finding, where it used to
  synthesize a grant with no call cap. Set `unlimited_calls_acknowledged: true` only after the
  user explicitly accepts unlimited calls. A positive `max_calls` together with the
  acknowledgement is refused as contradictory, with an `E_INVALID_DECISION` finding. Decisions
  documents that set `max_calls`, including every one this repository ships, are unaffected.
- **Contradictory lifetime decisions are refused.** A `valid_until_ledger` together with
  `no_expiry_acknowledged: true` used to synthesize the expiring grant and ignore the
  acknowledgement; it is now refused with an `E_INVALID_DECISION` finding, as is the call-cap
  pair above, so the user is asked which one they meant.
- **A second widening of one argument is refused.** An argument carries one bound. Synthesis
  applied the first widening that named a contract, function and argument index and silently
  ignored any other, so a cap and a floor meant as a range produced the cap alone. A decisions
  document that widens the same argument more than once is now refused with an
  `E_INVALID_DECISION` finding naming the argument. Documents that widen each argument at most
  once, including every one this repository ships, are unaffected.

A refused synthesis reports every finding in `details`; its top-level code is the first
finding's (`E_INVALID_DECISION` findings report `E_SPEC_INVALID` there), so read `details`.

- **Root-policy faults have their own error code.** `E_REGISTRY_ROOT_POLICY` is new. A registry
  roots configuration that is unparseable, holds a malformed, wrong-length or small-order (weak)
  key, or sets a threshold its keys cannot meet used to be reported as `E_REGISTRY_SIGNATURE`; it
  is now `E_REGISTRY_ROOT_POLICY`, from the CLI, from the MCP server's startup and from every tool
  that pins registry trust. So is the public development root configured for any network but
  testnet (below). `E_REGISTRY_SIGNATURE` keeps its meaning for snapshots whose signatures do not
  satisfy a usable policy. A client that matched `E_REGISTRY_SIGNATURE` to detect a bad roots
  configuration must match the new code.

## Security

- **The development registry root is refused outside testnet, everywhere.** Its signing key is
  derived from a published seed. Only the live checks and the operator account reader refused it
  for other networks; synthesis accepted a mainnet snapshot signed with it and stamped
  that root into the spec, and from there into the BuildManifest. Every registry trust built for a
  network other than testnet now refuses a root policy holding that key, alone or beside other
  keys, with `E_REGISTRY_ROOT_POLICY`.

- **The recognized smart account moves to OpenZeppelin 0.7.3**
  ([GHSA-jpg9-m7w4-c7wc](https://github.com/OpenZeppelin/stellar-contracts/security/advisories/GHSA-jpg9-m7w4-c7wc)).
  `stellar-accounts` before 0.7.3 approves a `Delegated` signer without any signature when it is
  the contract requesting the account's authorization, or when delegation loops back. The pinned
  account is now OpenZeppelin's multisig example built at v0.7.3
  (`203e2970d9fed24fb5fca2e0aeebb3c1e4648b76dd6601567178e6474c9fec6f`); the signed digest, storage
  layout and method inventory are unchanged, so wallet signing is unaffected. Development
  registry version 6 recognizes it and revokes the v0.7.2 build
  (`a12747ff6c139dc14fc2fd30d200d6bbb5da7b5d59812c047ce1f9cad226b289`) with the advisory as the
  reason; versions 1 to 5 are unchanged, and a checkpoint at version 5 extends to version 6.
  **Breaking:** an account running the v0.7.2 code is now refused: execution and the wallet
  accept only the pinned code, and the registry resolves it as revoked under version 6. Versions
  1 to 5 still recognize it and a caller may supply its own snapshot, so set
  `OZPB_REGISTRY_MIN_VERSION=6` (CLI `--registry-min-version 6`, wallet
  `registryMinimumVersion: 6`) or persist a version-6 checkpoint for the revocation to apply; the
  shipped configurations and documented commands now use 6. Recreate testnet accounts from the
  current code. The
  atomic live helper compiles in the account hash, so its reviewed hash changes too and an
  operator's `liveHelper` must name a helper deployed from the current source.

## Added

- **Registry governance tooling.** `ozpb registry keygen | successor | sign | combine | verify |
  monitor` for registry custodians and the operators who pin their roots, and the procedure in
  [Registry governance](../REGISTRY-GOVERNANCE.md). `registry/mainnet/` holds the draft, unsigned
  mainnet genesis and a placeholder root policy that every command refuses until the key ceremony.
- **Documentation by task and by reader.** A [documentation index](../README.md), a
  [user guide](../USER-GUIDE.md), a [tester quickstart](../TESTER-QUICKSTART.md),
  [scoping decisions](../SCOPING-DECISIONS.md), [trust boundaries](../TRUST-BOUNDARIES.md),
  [incident response](../INCIDENT-RESPONSE.md) and an [extension guide](../EXTENDING.md).
  [SECURITY.md](../../SECURITY.md) now describes what happens after a report and which versions
  are supported, both bounded to the grant period.
