# v1.0.0 release notes (draft)

Not yet released. Entries are added as changes land, in the commit that makes them.

1.0.0 is the release that delivers the third milestone, and the changes below are relative to
v0.1.0, the last release. The `v0.2.0-rc.1` and `v0.2.0-rc.2` pre-releases, made for the second
milestone's review, carried some of them; no v0.2.0 release follows them.

## Breaking changes

- **An uncapped grant needs an explicit acknowledgement.** `UserDecisions` gains
  `unlimited_calls_acknowledged`, mirroring `no_expiry_acknowledged`; an absent field reads as
  `false`. A decisions document with `max_calls: null` (or no `max_calls`) and no
  acknowledgement is now refused with an `E_NEEDS_DECISION` finding, where it used to
  synthesize a grant with no call cap. Set `unlimited_calls_acknowledged: true` only after the
  user explicitly accepts unlimited calls. A positive `max_calls` together with the
  acknowledgement is refused as contradictory, with an `E_INVALID_DECISION` finding. Decisions
  documents that set `max_calls`, including every one this repository ships, are unaffected.
- **Contradictory lifetime decisions are refused.** A `valid_until_ledger` together with
  `no_expiry_acknowledged: true` used to synthesize the expiring grant and ignore the
  acknowledgement; it is now refused with an `E_INVALID_DECISION` finding, as is the call-cap
  pair above, so the user is asked which one they meant.
- **A second widening of one argument is refused.** An argument carries one bound. Synthesis
  applied the first widening that named a contract, function and argument index and silently
  ignored any other, so a cap and a floor meant as a range produced the cap alone. A decisions
  document that widens the same argument more than once is now refused with an
  `E_INVALID_DECISION` finding naming the argument. Documents that widen each argument at most
  once, including every one this repository ships, are unaffected.
- **A cap on a signed amount needs its open floor acknowledged.** `Widening` gains
  `no_floor_acknowledged`, mirroring `unlimited_calls_acknowledged`; an absent field reads as
  `false`. A cap (`le_i128`) bounds an `i128`, a signed integer, from above only, so every negative
  amount passed the generated policy and only the target, or a composed spending limit for a
  transfer amount, could refuse it: the assumption behind OpenZeppelin's v0.7.0 audit finding L-06. Synthesis adds no floor of zero (that would infer a
  direction from the type) and one argument takes one bound, so a cap without the acknowledgement
  is now refused with an `E_NEEDS_DECISION` finding, where it used to synthesize. Set
  `no_floor_acknowledged: true` on the widening only after the user explicitly accepts that
  negative amounts pass. On a floor (`ge_i128`) or `any_value` it is refused with an
  `E_INVALID_DECISION` finding. The spec is unchanged: like the other acknowledgements, the field
  is a synthesis input, repeated in the rationale with what does refuse a negative amount. A cap an
  adapter derives needs no acknowledgement; the rationale now states its open floor too. The W3
  operator decisions file moves to `ozpb-soroswap-operator-decisions/v3`, whose `transfer_cap`
  requires `no_floor_acknowledged: true`; runs journaled under v2 still export as evidence, and an
  exported W3 report now records the decisions' schema and `transfer_cap_no_floor_acknowledged`.
- **A numeric bound must admit the recorded value.** A cap below the recorded amount, or a floor
  above it, used to synthesize a grant that refuses the very call it was built from; nothing
  checked. It is now refused with an `E_INVALID_DECISION` finding naming the argument, the bound
  and the recorded value; a bound equal to the recorded value is accepted. Every decisions
  document this repository ships keeps its bounds at or beyond the recorded values and is
  unaffected.

- **Every generated policy's Wasm hash changes, once and deliberately.** The generated crate
  root now states its provenance in three SEP-46 `contractmeta!` entries — `ozpb_generator`,
  `ozpb_template_family` and `ozpb_codegen_input` (the normalized codegen-input hash) — which
  `stellar contract info meta` prints. They are compiled into the Wasm, so a spec generated with
  this release builds to a different hash than with an earlier one, and an earlier release's
  deployed policy is reproduced only by that release. Normalized codegen-input hashes, and so
  the inputs that decide what a policy permits, are unchanged. The spec hash and registry
  snapshot are deliberately not in the meta: they would make each spec, registry update and
  account its own Wasm. They remain in the BuildManifest. Call-surface recognition rebuilds a
  generated policy from its spec and compares code hashes, so **a generated policy installed with
  an earlier release is no longer recognized** ("generated binding failed artifact
  reproduction"). Reinstall from this release's artifact, or check that account with the release
  that generated its policy.

- **BuildManifest schema 2, and every manifest hash changes.** `build-manifest/v2` (hashed under
  the `ozpb:v2:build-manifest` domain) adds `canonicalization_version`, `build_target` and a
  `producer` record: the toolkit's own source commit and dirty flag as its build recorded them
  (in the container image, which has no git checkout, the commit its build was given as
  `OZPB_TOOLKIT_SOURCE`; `null` when none was), the template-pack hash, and the
  image the disposable build worker ran (`null` when the API compiles in its own environment).
  A schema-1 manifest no longer parses, so it fails `verify` and generated-binding recognition:
  regenerate. A producer record that is not well formed (an image tag, a short or uppercase
  commit) does not parse either. `verify`
  and recognition now compare every field except `producer`, which describes the build that made
  the claim; a claim from another toolkit revision or another builder still reproduces, and
  `verify` says that its producer record differs. Worker mode: the launcher frame is now
  `contained-build-result/v2` with an `image` field, so install the API binary and
  `deployment/worker-launcher.py` from the same revision. This API cannot read an earlier
  launcher's `v1` frame, and an earlier API cannot read this launcher's. Either way the build
  fails, its removal claim is unread, and its slot stays retained. This API's error names the
  revision mismatch; an earlier API reports only unconfirmed cleanup. Once `OZPB_BUILD_JOBS`
  slots are held, worker mode accepts no builds until the operator installs a matching pair,
  confirms cleanup and restarts. This API also asks the launcher `--protocol` when it starts and
  refuses to start unless it answers `build-worker-job/v1 contained-build-result/v2`, so a
  mismatched pair installed before startup costs no slot. An earlier launcher takes no argument
  and is refused that way too; a launcher for another provider must implement the query
  ([launcher contract](../ISOLATED-BUILDS.md#launcher-contract-for-another-provider)).

A refused synthesis reports every finding in `details`; its top-level code is the first
finding's (`E_INVALID_DECISION` findings report `E_SPEC_INVALID` there), so read `details`.

- **Root-policy faults have their own error code.** `E_REGISTRY_ROOT_POLICY` is new. A registry
  roots configuration that is unparseable, holds a malformed, wrong-length or small-order (weak)
  key, or sets a threshold its keys cannot meet used to be reported as `E_REGISTRY_SIGNATURE`; it
  is now `E_REGISTRY_ROOT_POLICY`, from the CLI, from the MCP server's startup and from every tool
  that pins registry trust. So is the public development root configured for any network but
  testnet (below). `E_REGISTRY_SIGNATURE` keeps its meaning for snapshots whose signatures do not
  satisfy a usable policy. A client that matched `E_REGISTRY_SIGNATURE` to detect a bad roots
  configuration must match the new code.

## Security

- **A build no longer runs under a directory other users can write to.** Builds compiled in a
  fresh directory under the system temporary directory, and cargo reads `.cargo/config.toml` from
  every parent of the directory it runs in. On a multi-user Linux host any user could create
  `/tmp/.cargo/config.toml` naming a compiler wrapper, which then ran as whoever built: the CLI,
  a local MCP server or the wallet backend, each of which may read a 0600 key file, and a Wasm
  built that way reproduced under `verify` on the same host. A build directory is now created
  only under a directory that, like each of its parents, only root and the user can add entries
  to: the temporary directory when it qualifies (macOS's does), otherwise
  `ozpb/build-workspaces` in the user's cache directory. When neither qualifies the build is
  refused with `E_BUILD_UNAVAILABLE` before anything runs; set `TMPDIR` to a private directory.
  The Compose package and the disposable workers are unaffected.
- **The development registry root is refused outside testnet, everywhere.** Its signing key is
  derived from a published seed. Only the live checks and the operator account reader refused it
  for other networks; synthesis accepted a mainnet snapshot signed with it and stamped
  that root into the spec, and from there into the BuildManifest. Every registry trust built for a
  network other than testnet now refuses a root policy holding that key, alone or beside other
  keys, with `E_REGISTRY_ROOT_POLICY`.

- **The recognized smart account moves to OpenZeppelin 0.7.3**
  ([GHSA-jpg9-m7w4-c7wc](https://github.com/OpenZeppelin/stellar-contracts/security/advisories/GHSA-jpg9-m7w4-c7wc)).
  `stellar-accounts` before 0.7.3 approves a `Delegated` signer without any signature when it is
  the contract requesting the account's authorization, or when delegation loops back. The pinned
  account is now OpenZeppelin's multisig example built at v0.7.3
  (`203e2970d9fed24fb5fca2e0aeebb3c1e4648b76dd6601567178e6474c9fec6f`); the signed digest, storage
  layout and method inventory are unchanged, so wallet signing is unaffected. Development
  registry version 6 recognizes it and revokes the v0.7.2 build
  (`a12747ff6c139dc14fc2fd30d200d6bbb5da7b5d59812c047ce1f9cad226b289`) with the advisory as the
  reason; versions 1 to 5 are unchanged, and a checkpoint at version 5 extends to version 6.
  **Breaking:** an account running the v0.7.2 code is now refused: execution and the wallet
  accept only the pinned code, and the registry resolves it as revoked under version 6. Versions
  1 to 5 still recognize it and a caller may supply its own snapshot, so set
  `OZPB_REGISTRY_MIN_VERSION=6` (CLI `--registry-min-version 6`, wallet
  `registryMinimumVersion: 6`) or persist a version-6 checkpoint for the revocation to apply; the
  shipped configurations and documented commands now use 6. Recreate testnet accounts from the
  current code. The
  atomic live helper compiles in the account hash, so its reviewed hash changes too and an
  operator's `liveHelper` must name a helper deployed from the current source.
- **Dependency advisories.** `zerocopy`/`zerocopy-derive` move from 0.8.55 to 0.8.58
  (AIKIDO-2026-381234) in every lockfile that had them, including the lockfile emitted into each
  generated crate, and `mio` from 1.2.2 to 1.2.4 (AIKIDO-2026-88857) in the toolkit's. Neither is
  in the generated policy's Wasm dependency graph, so no Wasm hash moves; each BuildManifest's
  `lockfile_hash` does.

## Added

- **An inclusive range constraint for signed amounts.** `range_i128 {min, max}` admits
  `min <= x <= max`, so "spend up to X" can be stated as `0..=X` and the generated policy itself
  refuses a negative amount, which a cap (`le_i128`) leaves to the target. Validation refuses a
  range whose minimum exceeds its maximum (`E_SPEC_RANGE`), and a spending-limit composition
  needs the range to share an amount with `0..=limit`. The generated check is `x < min` then
  `x > max`, each refusing the tuple as the single bounds do; a comparison against `i128::MIN` or
  `i128::MAX` is left out, since no value lies beyond it (the type check stays). The evaluator and
  the harness's boundary cases cover both ends, one past each, `i128::MIN` and `i128::MAX`. Development registry version 7
  declares the kind in the scope template's `constraint_kinds`; versions 1 to 6 keep the
  vocabulary they were signed with, so a spec using a range is refused under them
  (`E_UNSUPPORTED_PATTERN`, naming the kind). The committed example and the mainnet draft are
  now version 7; documented registry floors stay at 6, which still admits it.
- **"Up to X" as a range decision.** A widening's bound may be `{"range_i128": {"min": "0",
  "max": "X"}}`: synthesis puts the range in the spec, asks no floor question for it, and refuses
  it together with `no_floor_acknowledged` (`E_INVALID_DECISION`). The policy-builder skill now
  offers "between 0 and X" first when a user caps an amount, and a cap with no floor only as the
  alternative the user explicitly accepts; it restates a range as `>= min and <= max`, which the
  transcript checker requires. A range synthesizes only under a registry that declares the kind
  (development version 7 and later).
- **Registry governance tooling.** `ozpb registry keygen | successor | sign | combine | verify |
  monitor` for registry custodians and the operators who pin their roots, and the procedure in
  [Registry governance](../REGISTRY-GOVERNANCE.md). `registry/mainnet/` holds the draft, unsigned
  mainnet genesis and a placeholder root policy that every command refuses until the key ceremony.
- **Documentation by task and by reader.** A [documentation index](../README.md), a
  [user guide](../USER-GUIDE.md), a [tester quickstart](../TESTER-QUICKSTART.md),
  [scoping decisions](../SCOPING-DECISIONS.md), [trust boundaries](../TRUST-BOUNDARIES.md),
  [incident response](../INCIDENT-RESPONSE.md) and an [extension guide](../EXTENDING.md).
  [SECURITY.md](../../SECURITY.md) now describes what happens after a report and which versions
  are supported, both bounded to the grant period.
- **Release binaries.** A published release now carries `ozpb`, `ozpb-mcp-server` and the native
  worker `ozpb-execution-runtime` for Linux x86_64, Linux aarch64 and macOS arm64, each archive
  with the licence files; `SHA256SUMS`; `ozpb-wire-contract-<tag>.json`, the tools the built
  server lists, with their input and output JSON Schemas, and the `E_*` codes; and a GitHub
  build-provenance attestation for every asset (`.github/workflows/release-binaries.yml`). The
  Linux binaries may need a glibc as new as Ubuntu 24.04's; the macOS ones are not signed or
  notarized. [Production release](../SELF-HOSTING.md#production-release) says how to verify and
  configure them, and how to upgrade.
- **A versioning policy.** [VERSIONING.md](../VERSIONING.md) says what 1.0 keeps stable within the
  1.x line during the grant period — the MCP wire contract, the CLI and operator configuration,
  the persisted formats and the generated artifacts — what counts as breaking, and the release
  gate.
- **Mainnet wallet sessions.** The wallet backend runs a session on mainnet from a mainnet
  operator configuration and a production build of the page: the operator's fee payer and the
  agent's delegate key from 0600 files, per-transaction, upload and session fee caps, production
  registry trust only, and a readiness check. On either network it can now remove a grant an
  earlier session installed, and on mainnet a removal is exempt from the session cap
  ([mainnet sessions](../POLLYWALLET-INTEGRATION.md#mainnet-sessions),
  [installing on mainnet](../MAINNET-INSTALL.md)).
- **An installed-grant check cron can alert on.** `ozpb check-installed-grant
  --recorded-authority-commitment <hex> --min-ledger <n>` compares the observation with the
  commitment the installation was approved against and exits 0 unchanged, 3 changed, 5 inactive
  (expired), 4 when the read or the check gave no answer or the observation is older than the
  floor, or 1 on an error before any read
  ([watching an installed grant](../INCIDENT-RESPONSE.md#watching-an-installed-grant)). Its JSON is
  unchanged, and without the flag it exits as before.
- **A mainnet acceptance gate map, checked in CI.** [MAINNET-GATES.md](../MAINNET-GATES.md) maps
  each acceptance gate before mainnet use to the tests that establish it, with its status and
  deviations. `scripts/check-mainnet-gates.sh` refuses the document when a named test is not in
  the file it cites, and runs each named test once by its full name.
- **Mutation testing.** `scripts/mutation-test.sh` (`cargo-mutants` 27.1.0) over the eight pure
  cores: a pull request fails when a mutant on a line it changed survives, and the whole set runs
  weekly (`.github/workflows/mutation.yml`).
- **Publishing a generated policy under its Wasm hash.** `ozpb publish-artifact` writes the
  generated crate exactly as `generate` emitted it, the spec, the BuildManifest and the Wasm,
  with a `SHA256SUMS` index, to `<out>/<wasm hash>/<build manifest hash>/`. It refuses files the
  manifest does not describe and a destination holding other content, and republishing the same
  build changes nothing. `ozpb verify-published` checks a published build and reproduces it
  through `verify`, exiting 0 when the report matches, 3 when it does not and 1 when the build
  is refused. New codes: `E_PUBLISH_PATH`, `E_PUBLISH_WASM_MISMATCH`,
  `E_PUBLISH_MANIFEST_MISMATCH`, `E_PUBLISH_INDEX_MISMATCH` and `E_PUBLISH_CONFLICT`
  ([publishing](../PUBLISHING.md)). The whole spec is published with a build, every rule in it,
  since the manifest binds its hash. Both commands work on local directories; the project
  publishes no build of its own.
- **Static-analysis triage.** [SAST-TRIAGE.md](../SAST-TRIAGE.md) records each static-analysis
  and leaked-secret item Aikido reported open: fixed, not exploitable (with where the flagged
  value comes from), or a false positive.

## The native worker is on a release candidate

The native worker (`ozpb-execution-runtime`, `execution-runtime/`) builds against
`soroban-sdk =30.0.0-rc.1`, with the stable host 30.0.0 in its lockfile; generated policies stay
on SDK 28.0.0 ([Soroban dependencies](../SOROBAN-DEPENDENCIES.md)). In this tree the worker is
still on that release candidate. 1.0.0 does not ship on it silently: before the release either
the worker moves to a stable SDK 30 and the protocol-30 compatibility gates are repeated
([protocol 30 validation](../PROTOCOL-30-VALIDATION.md#limits-and-follow-up)), or these notes
state that 1.0.0 ships its worker on the release candidate.
