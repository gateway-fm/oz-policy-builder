# v1.0.0 release notes (draft)

Not yet released. Entries are added as changes land, in the commit that makes them.

1.0.0 is the release that delivers the third milestone, and the changes below are relative to
v0.1.0, the last release. The `v0.2.0-rc.1` and `v0.2.0-rc.2` pre-releases, made for the second
milestone's review, carried some of them; no v0.2.0 release follows them.

## Breaking changes

Fixes that also break a contract stay under [Security](#security) or [Fixed](#fixed), each
marked **Breaking**.

- **An HTTP server needs a build launcher, or the operator's acceptance of compiling in its own
  trust domain.** `ozpb-mcp-server --http` without `OZPB_BUILD_WORKER_LAUNCHER` compiled every
  client's spec beside the API, with its credentials and network; that was intended only for the
  Compose package, and was also what a worker-mode host fell back to when its launcher was left
  unset. It now refuses to start that way unless `OZPB_HTTP_UNISOLATED_BUILDS=accept` is set,
  which the Compose file now does; any other value is refused. Stdio servers and the CLI are
  unchanged. Set the variable, or configure the launcher, before upgrading an HTTP deployment
  that does not use the shipped Compose file.
- **An uncapped grant needs an explicit acknowledgement.** `UserDecisions` gains
  `unlimited_calls_acknowledged`, mirroring `no_expiry_acknowledged`; an absent field reads as
  `false`. A decisions document with `max_calls: null` (or no `max_calls`) and no
  acknowledgement is now refused with an `E_NEEDS_DECISION` finding, where it used to
  synthesize a grant with no call cap. Set `unlimited_calls_acknowledged: true` only after the
  user explicitly accepts unlimited calls. A positive `max_calls` together with the
  acknowledgement is refused as contradictory, with an `E_INVALID_DECISION` finding. Decisions
  documents that set `max_calls`, including every one this repository ships, are unaffected.
- **Contradictory lifetime decisions are refused.** A `valid_until_ledger` together with
  `no_expiry_acknowledged: true` used to synthesize the expiring grant and ignore the
  acknowledgement; it is now refused with an `E_INVALID_DECISION` finding, as is the call-cap
  pair above, so the user is asked which one they meant.
- **A second widening of one argument is refused.** An argument carries one bound. Synthesis
  applied the first widening that named a contract, function and argument index and silently
  ignored any other, so a cap and a floor meant as a range produced the cap alone. A decisions
  document that widens the same argument more than once is now refused with an
  `E_INVALID_DECISION` finding naming the argument. Documents that widen each argument at most
  once, including every one this repository ships, are unaffected.
- **A cap on a signed amount needs its open floor acknowledged.** `Widening` gains
  `no_floor_acknowledged`, mirroring `unlimited_calls_acknowledged`; an absent field reads as
  `false`. A cap (`le_i128`) bounds an `i128`, a signed integer, from above only, so every negative
  amount passed the generated policy and only the target, or a composed spending limit for a
  transfer amount, could refuse it: the assumption behind OpenZeppelin's v0.7.0 audit finding L-06. Synthesis adds no floor of zero (that would infer a
  direction from the type) and one argument takes one bound, so a cap without the acknowledgement
  is now refused with an `E_NEEDS_DECISION` finding, where it used to synthesize. Set
  `no_floor_acknowledged: true` on the widening only after the user explicitly accepts that
  negative amounts pass. On a floor (`ge_i128`) or `any_value` it is refused with an
  `E_INVALID_DECISION` finding. The spec is unchanged: like the other acknowledgements, the field
  is a synthesis input, repeated in the rationale with what does refuse a negative amount. A cap an
  adapter derives needs no acknowledgement; the rationale now states its open floor too. The W3
  operator decisions file moves to `ozpb-soroswap-operator-decisions/v3`, whose `transfer_cap`
  requires `no_floor_acknowledged: true`; runs journaled under v2 still export as evidence, and an
  exported W3 report now records the decisions' schema and `transfer_cap_no_floor_acknowledged`.
- **A numeric bound must admit the recorded value.** A cap below the recorded amount, or a floor
  above it, used to synthesize a grant that refuses the very call it was built from; nothing
  checked. It is now refused with an `E_INVALID_DECISION` finding naming the argument, the bound
  and the recorded value; a bound equal to the recorded value is accepted. Every decisions
  document this repository ships keeps its bounds at or beyond the recorded values and is
  unaffected.
- **A widening may not contradict a reviewed adapter's role.** Where a target adapter bound to
  the target's code hash declares an argument a minimum output, synthesis applied any user bound
  there: a `range_i128` from 0 rated `low` on a Soroswap swap's `amount_out_min` removed the
  router's only slippage check and asked nothing. A bound that admits a value below the recorded
  minimum output (a lower floor, a range reaching below it, a cap, `any_value`), one that
  leaves a declared maximum input with no finite cap, and any widening of an argument the
  adapter keeps exact (the router's path and recipient, and `soroswap-router@2`'s deadline,
  where an `any_value` rated `high` used to synthesize) are now refused with an
  `E_INVALID_DECISION` finding naming the adapter and the role, whatever the blast radius.
  Raising a minimum output, capping an input at any finite amount, and a decision on a
  caller-chosen argument still apply. The W3 harness already floors the output at the recorded
  value, keeps the deadline and is unaffected.
- **A bound with no finite top must be rated high.** A widening's blast radius was the
  decision's own word for every bound but `any_value`: `ge_i128 {min: 0}` rated `low` on an
  amount allowed any amount. A bound with no finite top (a floor, or a cap or range ending at
  `i128::MAX`) rated `low` or `medium` is now refused with an `E_INVALID_DECISION` finding,
  except on an argument a reviewed adapter declares a minimum output. Spec validation
  also refuses a user-widened bound spanning the whole `i128` range unless it is rated `high`,
  with `E_SPEC_ANY_VALUE_BLAST_RADIUS`, as for `any_value`: a spec carrying one at `low` or
  `medium`, from any producer, no longer validates. The library's synthetic W3 walkthrough now
  rates its output floor `high`, since it binds no adapter; its spec hash changes, its generated
  policy does not (provenance is not codegen input).
- **A range from `i128::MIN` needs the open-floor acknowledgement.** The generated check leaves
  out a comparison against the type's own minimum, so `range_i128 {min: i128::MIN, max: N}`
  renders exactly the cap at N, yet synthesized without the acknowledgement a cap requires. It now
  asks the cap's `E_NEEDS_DECISION` question and accepts `no_floor_acknowledged: true`.
- **A widening that would loosen several recorded calls is refused.** A widening names a
  contract, function and argument, not a recorded call, so it applied to every distinct call of
  that function: widening one payment's amount to `0..=2000` raised another recipient's payment
  to 2000 as well. A widening that would apply to more than one distinct permitted call is now
  refused with an `E_INVALID_DECISION` finding; recorded calls that differ only in the widened
  argument are one permitted call and are unaffected, as is every decisions document this
  repository ships.

- **Every generated policy's Wasm hash changes, once and deliberately.** The generated crate
  root now states its provenance in three SEP-46 `contractmeta!` entries — `ozpb_generator`,
  `ozpb_template_family` and `ozpb_codegen_input` (the normalized codegen-input hash) — which
  `stellar contract info meta` prints. They are compiled into the Wasm, so a spec generated with
  this release builds to a different hash than with an earlier one, and an earlier release's
  deployed policy is reproduced only by that release. Normalized codegen-input hashes, and so
  the inputs that decide what a policy permits, are unchanged. The spec hash and registry
  snapshot are deliberately not in the meta: they would make each spec, registry update and
  account its own Wasm. They remain in the BuildManifest. Call-surface recognition rebuilds a
  generated policy from its spec and compares code hashes, so **a generated policy installed with
  an earlier release is no longer recognized** ("generated binding failed artifact
  reproduction"). Reinstall from this release's artifact, or check that account with the release
  that generated its policy. Separately, a policy for a grant with no call cap carries a
  corrected comment above its TTL extension, which used to say the Wasm code entry is not
  extended: `instance().extend_ttl` extends it with the instance. The comment keeps its line
  count, so only such a crate's source hash moves; no committed generated crate lacks a call cap.

- **BuildManifest schema 2, and every manifest hash changes.** `build-manifest/v2` (hashed under
  the `ozpb:v2:build-manifest` domain) adds `canonicalization_version`, `build_target` and a
  `producer` record: the toolkit's own source commit and dirty flag as its build recorded them
  (in the container image, which has no git checkout, the commit its build was given as
  `OZPB_TOOLKIT_SOURCE`; `null` when none was), the template-pack hash, and the
  image the disposable build worker ran (`null` when the API compiles in its own environment).
  A schema-1 manifest no longer parses, so it fails `verify` and generated-binding recognition:
  regenerate. A producer record that is not well formed (an image tag, a short or uppercase
  commit) does not parse either. `verify`
  and recognition now compare every field except `producer`, which describes the build that made
  the claim; a claim from another toolkit revision or another builder still reproduces, and
  `verify` says that its producer record differs. Worker mode: the launcher frame is now
  `contained-build-result/v2` with an `image` field, so install the API binary and
  `deployment/worker-launcher.py` from the same revision. This API cannot read an earlier
  launcher's `v1` frame, and an earlier API cannot read this launcher's. Either way the build
  fails, its removal claim is unread, and its slot stays retained. This API's error names the
  revision mismatch; an earlier API reports only unconfirmed cleanup. Once `OZPB_BUILD_JOBS`
  slots are held, worker mode accepts no builds until the operator installs a matching pair,
  confirms cleanup and restarts. This API also asks the launcher `--protocol` when it starts and
  refuses to start unless it answers `build-worker-job/v1 contained-build-result/v2`, so a
  mismatched pair installed before startup costs no slot. An earlier launcher takes no argument
  and is refused that way too; a launcher for another provider must implement the query
  ([launcher contract](../ISOLATED-BUILDS.md#launcher-contract-for-another-provider)).

A refused synthesis reports every finding in `details`; its top-level code is the first
finding's (`E_INVALID_DECISION` findings report `E_SPEC_INVALID` there), so read `details`.

- **Root-policy faults have their own error code.** `E_REGISTRY_ROOT_POLICY` is new. A registry
  roots configuration that is unparseable, holds a malformed, wrong-length or small-order (weak)
  key, or sets a threshold its keys cannot meet used to be reported as `E_REGISTRY_SIGNATURE`; it
  is now `E_REGISTRY_ROOT_POLICY`, from the CLI, from the MCP server's startup and from every tool
  that pins registry trust. So is the public development root configured for any network but
  testnet (below). `E_REGISTRY_SIGNATURE` keeps its meaning for snapshots whose signatures do not
  satisfy a usable policy. A client that matched `E_REGISTRY_SIGNATURE` to detect a bad roots
  configuration must match the new code.
- **Six nullable fields are published as nullable.** The server sends an explicit `null` for an
  install intent's `valid_until_ledger` and a grant's `valid_until` when the grant does not expire,
  for an authority entry's or restricted-key rule's `valid_until`, for a finding's `rule_id` when
  it is about the new rule, and for a verifier observation's `scheme` when the code is not a
  recognized verifier. The JSON Schemas the server lists required these fields but refused `null`,
  so a client validating a no-expiry intent against the published output schema rejected it. They
  now admit `null`. The wire is unchanged; the schema's type for each field is not, so a client
  that generated types from an earlier schema must regenerate them and handle `null`.
- **Recordings are `recording/v2`, and a `recording/v1` bundle is refused.** A v2 bundle keeps
  the transaction result's XDR, and verification rebuilds its execution and simulation summaries
  from the preserved raw evidence, so an edited summary no longer verifies. A v1 bundle, which
  v0.1.0 wrote, kept too little to recheck its outcome: it now fails verification with
  `E_EVIDENCE_INCOHERENT`. Record the transaction again while RPC still retains it, or reimport its
  raw evidence ([existing artifacts](../RECORDING-EVIDENCE.md#existing-artifacts)). Recording
  hashes change with the schema, and so does the hash of every spec that cites a recording.
- **`E_ADMIN_RULE_UNSAFE` is withdrawn.** v0.1.0's code list carried it, but no v0.1.0 tool
  returned it, and the [wire contract](../wire-contract.json) no longer names it. The authority
  check the install tools now run lists every rule that can change the account, and refuses with
  `E_UNSUPPORTED_AUTHORITY`, `E_DELEGATE_HAS_AUTHORITY` or `E_DELEGATE_GRANT_OVERLAP`. A client
  that matches the published code list should drop it.

## Security

- **An adapter-bound rule's target code is checked at install, with a new error code.** When a
  rule's caps come from a reviewed target adapter, or its spec refuses target drift, the install
  intent now reads the target's code in the same account read and refuses other code with
  `E_TARGET_CODE_CHANGED`. The wire contract (`docs/wire-contract.json`) names it, and the three
  authority tools' descriptions say so. The code is additive (a client that does not know it
  treats it as a failure); the refusal is not. **Breaking:** an install intent that earlier
  builds prepared for such a rule over changed target code is now refused.
- **A build no longer runs under a directory other users can write to.** Builds compiled in a
  fresh directory under the system temporary directory, and cargo reads `.cargo/config.toml` from
  every parent of the directory it runs in. On a multi-user Linux host any user could create
  `/tmp/.cargo/config.toml` naming a compiler wrapper, which then ran as whoever built: the CLI,
  a local MCP server or the wallet backend, each of which may read a 0600 key file, and a Wasm
  built that way reproduced under `verify` on the same host. A build directory is now created
  only under a directory that, like each of its parents, only root and the user can add entries
  to: the temporary directory when it qualifies (macOS's does), otherwise `ozpb/build` in the
  user's cache directory; a `.cargo` (other than the user's cargo home) or `Cargo.toml` already
  in one of those parents is refused too. When neither qualifies the build is refused with
  `E_BUILD_UNAVAILABLE` before anything runs; set `TMPDIR` to a private directory. The default build cache moves with
  it, so on Linux it is now `~/.cache/ozpb/build/ozpb-build-cache-<uid>` rather than under `/tmp`,
  and the first build there is cold. Where `~/.cache` is group-writable (a umask of 002 can
  leave it so), the fallback is refused too: set `TMPDIR` to a private directory. The Compose
  package and the disposable workers are unaffected. **Breaking:** where neither directory
  qualifies, a build that earlier releases ran is refused.
- **The reference suite is bounded.** Validation bounds each part of a spec, not the suite they
  compose into, and tuple cross products grow with the square of a function's tuples times their
  arity: a 991 KB spec within every per-item limit (14 rules of 32 tuples of 32 exact amounts)
  derived 310,674 cases, held about 1 GB and answered with 74 MB, through a tool a hosted server
  admits 60 times a minute. Few cases can be large too, since each copies the tuple it varies: a
  397 KB spec whose one large tuple carries four 60 KiB values derived 19,245 cases and held
  510 MB. `reference_suite`, its `--emit-cases` form, `verify` and `prepare_dry_run` now size the
  suite first and refuse one over 20,000 cases, or over an estimated 64 MiB of case data, with
  `E_SPEC_INVALID` and an `E_SPEC_LIMITS` finding giving both figures, before anything is derived
  or built. The largest committed spec derives 65 cases. **Breaking:** a spec over either bound,
  which earlier builds derived and built, is refused.
- **A hosted server no longer forwards an RPC endpoint's words.** `record_transaction`,
  `record_simulation`, `preflight_transaction` and `assemble_install_transaction` returned a
  failed read's text as it came: a transport error quotes the full URL, path included, where
  providers put API keys, and JSON-RPC messages, data and reported network names passed through,
  so any bearer-token holder could read the operator's endpoint credentials. An `--http` server
  now gives every failed read its code and a fixed description, as the authority scan and target
  capture already did; refusals of the caller's own envelope keep their wording, and a stdio
  server still reports the endpoint's words. A hosted `record_simulation` also refuses an envelope
  carrying signatures or signed authorization entries before any request, as `preflight_transaction`
  did (`E_UNSUPPORTED_ENVELOPE`), and the tool's description in the wire contract says so;
  `MAINNET-GATES.md` claimed both for G12 before either held. **Breaking:** a hosted
  `record_simulation` of a signed envelope, which earlier builds simulated, is refused; the
  changed error text is not versioned.
- **A hosted server's local builds leave nothing for the next client.** A failed build returned
  up to 64 KiB of the compiler's output, host paths included, to the client; an `--http` server
  now returns the exit status alone, as a disposable worker does. Each distinct spec name left
  about 100 KB of outputs in the shared build cache for good, so a client could fill the Compose
  package's 2 GiB cache by naming specs; each such build now removes its own crate's outputs and
  keeps the dependencies, one build at a time. The CLI and stdio servers keep both.
- **A missing toolchain component is refused, not downloaded.** The image and the worker
  launcher set `RUSTUP_AUTO_INSTALL=0`, but the build environment's allowlist dropped it, so
  rustup could fetch a missing component during a build; it now reaches rustup.
- **The development registry root is refused outside testnet, everywhere.** Its signing key is
  derived from a published seed. Only the live checks and the operator account reader refused it
  for other networks; synthesis accepted a mainnet snapshot signed with it and stamped
  that root into the spec, and from there into the BuildManifest. Every registry trust built for a
  network other than testnet now refuses a root policy holding that key, alone or beside other
  keys, with `E_REGISTRY_ROOT_POLICY`. **Breaking:** synthesis for any network but testnet under
  such a root policy, which earlier releases accepted, is refused.
- **Code revoked by its hash is refused wherever a policy is recognized.** Custodians revoke one
  generated build as `policy/<wasm hash>`, and `ozpb registry monitor --wasm-hash` reported it
  revoked, but a generated policy was recognized through its template family alone, so the
  authority check, the install intent and assembly, installed-grant monitoring and
  `check_against_policy` still recognized that build. A policy binding is now refused with
  `E_REGISTRY_REVOKED` when its code hash is revoked under any role (`policy`, `account`,
  `verifier` or `target_adapter`), as the monitor treats it. A policy installed on another rule
  whose code is revoked that way is no longer recognized, so its rule on the grant's target is
  refused as an overlap, and synthesis refuses to compose a spending limit so revoked
  (`E_REGISTRY_REVOKED`). **Breaking:** a binding or composition that earlier builds accepted is
  refused once its code hash is revoked.
- **A policy's signer semantics come from its reviewed build, not its label.** The authority check
  read any recognized policy whose signed registry entry said `oz:spending_limit` as requiring at
  least one of its rule's own signers. That was reviewed for one build, OpenZeppelin's spending
  limit at the pinned hash, so a rule on the grant's target behind another build with that label
  was listed as a note when it should have refused the installation: an unreviewed policy there
  may admit the agent with no signature. The semantics are now compiled in for that hash and kind
  only; any other policy's are unknown, and such a rule on the target refuses the installation
  with `E_DELEGATE_GRANT_OVERLAP`. **Breaking:** an installation the v0.2.0 pre-releases allowed
  beside such a rule is refused.

- **The recognized smart account moves to OpenZeppelin 0.7.3**
  ([GHSA-jpg9-m7w4-c7wc](https://github.com/OpenZeppelin/stellar-contracts/security/advisories/GHSA-jpg9-m7w4-c7wc)).
  `stellar-accounts` before 0.7.3 approves a `Delegated` signer without any signature when it is
  the contract requesting the account's authorization, or when delegation loops back. The pinned
  account is now OpenZeppelin's multisig example built at v0.7.3
  (`203e2970d9fed24fb5fca2e0aeebb3c1e4648b76dd6601567178e6474c9fec6f`); the signed digest, storage
  layout and method inventory are unchanged, so wallet signing is unaffected. Development
  registry version 6 recognizes it and revokes the v0.7.2 build
  (`a12747ff6c139dc14fc2fd30d200d6bbb5da7b5d59812c047ce1f9cad226b289`) with the advisory as the
  reason; versions 1 to 5 are unchanged, and a checkpoint at version 5 extends to version 6.
  **Breaking:** an account running the v0.7.2 code is now refused: execution and the wallet
  accept only the pinned code, and the registry resolves it as revoked under version 6. Versions
  1 to 5 still recognize it and a caller may supply its own snapshot, so set
  `OZPB_REGISTRY_MIN_VERSION=6` (CLI `--registry-min-version 6`, wallet
  `registryMinimumVersion: 6`) or persist a version-6 checkpoint for the revocation to apply; the
  shipped configurations and documented commands now use 6. Recreate testnet accounts from the
  current code. The
  atomic live helper compiles in the account hash, so its reviewed hash changes too and an
  operator's `liveHelper` must name a helper deployed from the current source.
- **A recording counts only the authorization entries the network checked.** The host
  authenticates an entry only when a `require_auth` reaches it, and a transaction succeeds with
  entries nothing used. The recorder copied every entry of an executed envelope into
  `authorizations`. Anyone could attach an entry naming another account and a payment out of it,
  with a garbage signature, to their own successful transaction, and the recording presented it
  as that account's `rpc_reported` authorization. Synthesis could then derive that account as
  the authorizer. An executed address credential is now authorization evidence only when the
  operation's meta shows its nonce consumed. Any other entry is an `evidence_notes` line and
  never an authorizer ([recording evidence](../RECORDING-EVIDENCE.md#which-authorization-entries-are-evidence)).
  The checked entries of a successful network transaction are unaffected: all ten mainnet
  corpus transactions record the same authorizations. **Breaking:** a failed network transaction
  recorded with `allow_failed` (its meta records no operation changes), or an executed import
  without result meta, no longer lists its address credentials as authorizations. A
  `recording/v2` bundle saved from an earlier build that lists such an entry, or a source-account
  credential of an operation that names its own source (below), no longer verifies
  (`E_EVIDENCE_INCOHERENT`): record it again or reimport its raw evidence. The synthetic recorder
  fixture now carries its nonce in the meta, so `docs/examples/import-bundle.json` and the
  recording hashes derived from the fixture change.
- **A source-account credential belongs to the operation's source.** It was attributed to the
  transaction's source account even when the operation names its own, which is the account the
  host runs it as. It now resolves to the operation's source account, and to the (inner)
  transaction's only when the operation names none.
- **Dependency advisories.** `zerocopy`/`zerocopy-derive` move from 0.8.55 to 0.8.58
  (AIKIDO-2026-381234) in every lockfile that had them, including the lockfile emitted into each
  generated crate, and `mio` from 1.2.2 to 1.2.4 (AIKIDO-2026-88857) in the toolkit's. Neither is
  in the generated policy's Wasm dependency graph, so no Wasm hash moves; each BuildManifest's
  `lockfile_hash` does. **Breaking**, as a change to the generated artifact of every existing
  spec, and covered by the provenance and BuildManifest changes under
  [Breaking changes](#breaking-changes), which already change every generated Wasm and manifest
  in this release.

## Added

- **An inclusive range constraint for signed amounts.** `range_i128 {min, max}` admits
  `min <= x <= max`, so "spend up to X" can be stated as `0..=X` and the generated policy itself
  refuses a negative amount, which a cap (`le_i128`) leaves to the target. Validation refuses a
  range whose minimum exceeds its maximum (`E_SPEC_RANGE`), and a spending-limit composition
  needs the range to share an amount with `0..=limit`. The generated check is `x < min` then
  `x > max`, each refusing the tuple as the single bounds do; a comparison against `i128::MIN` or
  `i128::MAX` is left out, since no value lies beyond it (the type check stays). The evaluator and
  the harness's boundary cases cover both ends, one past each, `i128::MIN` and `i128::MAX`. Development registry version 7
  declares the kind in the scope template's `constraint_kinds`; versions 1 to 6 keep the
  vocabulary they were signed with, so a spec using a range is refused under them
  (`E_UNSUPPORTED_PATTERN`, naming the kind). The committed example and the mainnet draft are
  now version 7; documented registry floors stay at 6, which still admits it.
- **The card shows each bound beside the recorded value.** Synthesis's rationale line for a
  user's numeric bound now ends `; recorded value <N>`, and the policy-builder skill's card sets
  each bound beside it under **Not constrained**, with the bound's maximum as a multiple of the
  recorded value; the transcript checker requires the value there. A finite bound's rating stays
  the user's however large it is, so this is how a cap far beyond the recording is seen.
- **"Up to X" as a range decision.** A widening's bound may be `{"range_i128": {"min": "0",
  "max": "X"}}`: synthesis puts the range in the spec, asks no floor question for it, and refuses
  it together with `no_floor_acknowledged` (`E_INVALID_DECISION`), unless the range starts at
  `i128::MIN` and so has no floor (above). The policy-builder skill now
  offers "between 0 and X" first when a user caps an amount, and a cap with no floor only as the
  alternative the user explicitly accepts; it restates a range as `>= min and <= max`, which the
  transcript checker requires. A range synthesizes only under a registry that declares the kind
  (development version 7 and later).
- **Registry governance tooling.** `ozpb registry keygen | successor | sign | combine | verify |
  monitor` for registry custodians and the operators who pin their roots, and the procedure in
  [Registry governance](../REGISTRY-GOVERNANCE.md). `registry/mainnet/` holds the draft, unsigned
  mainnet genesis and a placeholder root policy that every command refuses until the key ceremony.
- **Documentation by task and by reader.** A [documentation index](../README.md), a
  [user guide](../USER-GUIDE.md), a [tester quickstart](../TESTER-QUICKSTART.md),
  [scoping decisions](../SCOPING-DECISIONS.md), [trust boundaries](../TRUST-BOUNDARIES.md),
  [incident response](../INCIDENT-RESPONSE.md) and an [extension guide](../EXTENDING.md).
  [SECURITY.md](../../SECURITY.md) now describes what happens after a report and which versions
  are supported, both bounded to the grant period.
- **Release binaries.** A published release now carries `ozpb`, `ozpb-mcp-server` and the native
  worker `ozpb-execution-runtime` for Linux x86_64, Linux aarch64 and macOS arm64, each archive
  with the licence files; `SHA256SUMS`; `ozpb-wire-contract-<tag>.json`, the tools the built
  server lists, with their input and output JSON Schemas, and the `E_*` codes; and a GitHub
  build-provenance attestation for every asset (`.github/workflows/release-binaries.yml`). The
  Linux binaries may need a glibc as new as Ubuntu 24.04's; the macOS ones are not signed or
  notarized. [Production release](../SELF-HOSTING.md#production-release) says how to verify and
  configure them, and how to upgrade.
- **A versioning policy.** [VERSIONING.md](../VERSIONING.md) says what 1.0 keeps stable within the
  1.x line during the grant period — the MCP wire contract, the CLI and operator configuration,
  the persisted formats and the generated artifacts — what counts as breaking, and the release
  gate.
- **The wire contract is committed and checked.** [`docs/wire-contract.json`](../wire-contract.json)
  is the tree's own MCP wire contract: the export a release attaches, without its `release` and
  `commit`. CI rebuilds the server, regenerates it through that export
  (`scripts/release-artifacts.py check-wire-contract`) and fails on any difference, and an
  `api-types` test pins every published `E_*` code to it without a server build. An intended
  change regenerates the file and records here whether it is breaking
  ([keeping the snapshot current](../VERSIONING.md#keeping-the-snapshot-current)).
- **TypeScript types for the install surface.** `wallet/shared/install-wire.d.mts` declares the
  requests and responses of `prepare_install_intent` and `assemble_install_transaction` for a
  wallet other than Pollywallet; a wallet test fails when they differ from the committed schemas
  ([another wallet](../POLLYWALLET-INTEGRATION.md#another-wallet-the-typed-install-surface)).
- **Mainnet wallet sessions.** The wallet backend runs a session on mainnet from a mainnet
  operator configuration and a production build of the page: the operator's fee payer and the
  agent's delegate key from 0600 files, per-transaction, upload and session fee caps, production
  registry trust only, and a readiness check. On either network it can now remove a grant an
  earlier session installed, and on mainnet a removal is exempt from the session cap
  ([mainnet sessions](../POLLYWALLET-INTEGRATION.md#mainnet-sessions),
  [installing on mainnet](../MAINNET-INSTALL.md)).
- **An installed-grant check cron can alert on.** `ozpb check-installed-grant
  --recorded-authority-commitment <hex> --min-ledger <n>` compares the observation with the
  commitment the installation was approved against and exits 0 unchanged, 3 changed, 5 inactive
  (expired), 4 when the read or the check gave no answer or the observation is older than the
  floor, or 1 on an error before any read
  ([watching an installed grant](../INCIDENT-RESPONSE.md#watching-an-installed-grant)). Its JSON is
  unchanged, and without the flag it exits as before.
- **A mainnet acceptance gate map, checked in CI.** [MAINNET-GATES.md](../MAINNET-GATES.md) maps
  each acceptance gate before mainnet use to the tests that establish it, with its status and
  deviations. `scripts/check-mainnet-gates.sh` refuses the document when a named test is not in
  the file it cites, and runs each named test once by its full name.
- **Mutation testing.** `scripts/mutation-test.sh` (`cargo-mutants` 27.1.0) over the eight pure
  cores: a pull request fails when a mutant on a line it changed survives, and the whole set runs
  weekly (`.github/workflows/mutation.yml`).
- **Publishing a generated policy under its Wasm hash.** `ozpb publish-artifact` writes the
  generated crate exactly as `generate` emitted it, the spec, the BuildManifest and the Wasm,
  with a `SHA256SUMS` index, to `<out>/<wasm hash>/<build manifest hash>/`. It refuses files the
  manifest does not describe and a destination holding other content, and republishing the same
  build changes nothing. `ozpb verify-published` checks a published build and reproduces it
  through `verify`, exiting 0 when the report matches, 3 when it does not and 1 when the build
  is refused. New codes: `E_PUBLISH_PATH`, `E_PUBLISH_WASM_MISMATCH`,
  `E_PUBLISH_MANIFEST_MISMATCH`, `E_PUBLISH_INDEX_MISMATCH` and `E_PUBLISH_CONFLICT`
  ([publishing](../PUBLISHING.md)). The whole spec is published with a build, every rule in it,
  since the manifest binds its hash. Both commands work on local directories; the project
  publishes no build of its own.
- **Static-analysis triage.** [SAST-TRIAGE.md](../SAST-TRIAGE.md) records each static-analysis
  and leaked-secret item Aikido reported open: fixed, not exploitable (with where the flagged
  value comes from), or a false positive.

## Fixed

- **A rule with several tuples of one function generates lint-clean code.** The emitter repeated
  the function's guard for each tuple, `(fn_0_ok && check_call_0(..)) || (fn_0_ok &&
  check_call_1(..))`, which `clippy::nonminimal_bool` refuses under `-D warnings`. It now reads
  each guard once, `fn_0_ok && (check_call_0(..) || check_call_1(..))`. What the policy permits,
  and the order its checks run in, are unchanged, and so is the generated source of every rule
  whose functions have one tuple each. The committed two-payment fixture is linted in CI with the
  other generated crates. **Breaking**, since such a rule's generated source and Wasm change, and
  covered by the provenance change under [Breaking changes](#breaking-changes), which already
  changes every generated Wasm in this release.

## The native worker ships on a release candidate

1.0.0 ships the native worker (`ozpb-execution-runtime`, `execution-runtime/`) built against
`soroban-sdk =30.0.0-rc.1`, with the stable host 30.0.0 in its lockfile. The release candidate
is off-chain only: generated policies and the live helper stay on SDK 28.0.0, and the
recognized account and verifier Wasm are unchanged ([Soroban dependencies](../SOROBAN-DEPENDENCIES.md)).

The stable SDK 30.0.0, published on 24 November 2026, requires `soroban-env-host =30.0.1`, so
moving to it changes the host as well as the SDK. Both are in the dependency inventory reviewed
for the [RUSTSEC-2026-0387 risk acceptance](../SECURITY-EXCEPTIONS.md), and the supply-chain gate
refuses the worker's lockfile once they change. Moving it needs the maintainer to reassess that
acceptance for host 30.0.1 and the protocol-30 compatibility gates repeated on the stable SDK
([protocol 30 validation](../PROTOCOL-30-VALIDATION.md#limits-and-follow-up)); until then it stays
on the release candidate.
